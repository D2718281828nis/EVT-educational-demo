# Исследование экстремумов с Graph-EVT-agent

Учебный модуль показывает полный, но компактный исследовательский процесс на
двух синтетических наборах и разделяет ноутбуки на два самостоятельных
маршрута по каталогам:

- `notebooks/1-d/` — одномерный ряд `data/generated/additive_fractal_series.csv`
  (детерминированная сумма трёх синусоид плюс Hurst/DFA-окрашенный экстремальный
  впрыск плюс простой гауссовский шум — все три слагаемых хранятся в CSV
  отдельными колонками; см. ноутбук 1);
- `notebooks/n-d/` — многоканальный ряд `data/generated/kuramoto_propagation_series.csv`
  (Kuramoto-фон плюс один впрыснутый Hurst/DFA-окрашенный импульс, распространяющийся
  от известного исходного канала; см. раздел "Как `source_channel` и `event_onset`
  связаны" ниже).

Каждый маршрут проходит аудит данных, диагностику зависимости, POT/EVT-анализ,
LLM-проверку результата, анализ чувствительности спецификаций и выпуск
воспроизводимого отчёта; маршрут `n-d` дополнительно показывает граф
зависимостей, локализацию источника и обучение GNN/GAT — этапы, которые для
одного канала закономерно недоступны. Оба маршрута теперь используют
oracle-assisted baseline (известный `event_onset`/`event_start`) и явно
сверяют детекцию и (для `n-d`) локализацию источника с синтетической истиной.
EVT-конвейер берётся из
[Graph-EVT-agent](https://github.com/D2718281828nis/Graph-EVT-agent), а не
копируется в ноутбуки.

> Это учебный синтетический пример. У ряда нет предметной интерпретации и
> опубликованной разметки экстремумов; результаты нельзя использовать для
> инженерных, финансовых или иных решений.

## Установка

Из корня этого репозитория:

```bash
python -m venv demo/evt-educational-demo/.venv
source demo/evt-educational-demo/.venv/bin/activate
python -m pip install -r demo/evt-educational-demo/requirements.txt
python -m pip install --no-deps -e demo/evt-educational-demo
```

Последняя строка `requirements.txt` устанавливает Graph-EVT-agent напрямую из
его GitHub-репозитория на актуальном commit `465b231` с API разметки эпизодов,
обучения GNN/GAT (включая temporal-графы для 1-D, `train_1d`) и progress bars
(`tqdm`). Численное ядро библиотеки детерминировано: ноутбуки
используют `EVTConfig`, `GraphConfig`, `InputConfig` и `GraphEVTPipeline`. В
ноутбуке 04 дополнительно показан настоящий LLM-режим `EVTAgentTeam` с
`MistralClient`: для его включения задайте `MISTRAL_API_KEY` только через
окружение. Локально скопируйте `.env.example` в `.env`, внесите новый ключ в
`.env` (этот файл исключён из Git), затем из каталога модуля запустите:

```bash
set -a
source .env
set +a
jupyter lab
```

Перезапустите kernel ноутбука после изменения окружения. Без ключа LLM-вызов
явно пропускается, а численный анализ доступен.

## Маршрут по ноутбукам

Запускайте ноутбуки по порядку из каталога модуля:

```bash
cd demo/evt-educational-demo
jupyter lab
```

### `notebooks/1-d/` — одномерный ряд (`additive_fractal_series.csv`)

1. `01_dataset_audit.ipynb` — схема, качество и обзор ряда; включает
   аддитивную декомпозицию на 3 подграфика (осцилляторы / экстремальный
   впрыск / простой шум), читая их прямо из колонок CSV;
2. `02_scaling_and_dependence.ipynb` — structure functions и ограничения
   утверждений о фрактальности;
3. `03_evt_detection.ipynb` — одноканальный POT/GPD-анализ `GraphEVTPipeline`;
4. `04_llm_hypothesis_agent.ipynb` — LLM-команда объясняет и проверяет численный результат;
5. `05_specification_robustness.ipynb` — анализ чувствительности EVT-спецификаций;
6. `06_reproducible_report.ipynb` — отчёт, manifest и provenance;
7. `07_evaluation_orchestrator.ipynb` — `EvaluationCase`/`EvaluationOrchestrator`
   на единственном известном случае, включая локализацию начальной точки
   через `graph_evt_agent.evt.find_events`;
8. `08_library_utilities.ipynb` — обзор возможностей библиотеки, не
   задействованных в ноутбуках 1–7: загрузчик `load_csv`/`TimeSeriesInput`,
   `progress_callback`, встроенные графики `plot_detection`/`plot_evaluation`
   рядом с собственными, и обработка пропусков `InputConfig(missing=...)` на
   синтетически повреждённом ряде;
9. `09_temporal_graph_gnn_gat.ipynb` — `graph_evt_agent.temporal`
   (commit `465b231`): превращает время в узлы графа, обучает GNN/GAT через
   `ProcessModelTrainer.train_1d` той же инфраструктурой, что и `n-d/09`
   (группы, метрики, `GraphProcessModel.save`/`.load`), и явно отображает
   предсказанный узел обратно в окно времени на реальном ряде.

### `notebooks/n-d/` — многоканальный ряд (`kuramoto_propagation_series.csv`)

1. `01_dataset_audit.ipynb` — схема, качество и обзор всех каналов (разметка
   `is_extreme` видна в схеме, но намеренно не используется здесь);
2. `02_synchronization_and_dependence.ipynb` — межканальная корреляция и её
   динамика во времени;
3. `03_evt_detection.ipynb` — многоканальный POT/GPD-анализ с графом и
   ranking; baseline заканчивается точно перед известным `event_onset`
   (oracle-assisted), а оценённый источник сверяется с `source_channel`;
4. `04_llm_hypothesis_agent.ipynb` — LLM-проверка результата относительно
   известного времени события и источника;
5. `05_specification_robustness.ipynb` — анализ чувствительности: на этом
   ряде `persistence=1` находит верный источник, а `persistence=2` —
   ошибается (ближайший сосед по кольцу) — конкретная, воспроизводимая
   демонстрация того, почему спецификация влияет не только на детекцию;
6. `06_reproducible_report.ipynb` — отчёт, manifest и provenance с графом,
   источником и сверкой с истиной;
7. `07_detection_and_source_visualization.ipynb` — многоканальная фигура,
   связывающая EVT-порог, момент тревоги, отклики и ranking источника;
8. `08_agent_pipeline_graph.ipynb` — исполняемый граф маршрута агента, запуск
   на данных и визуализация оценённой сети каналов;
9. `09_gnn_gat_process_modeling.ipynb` — обучение GNN/GAT на независимых
   размеченных эпизодах; затем показывает, что переиспользование
   baseline-размера обучающих эпизодов (`300`) на этом более медленно
   синхронизирующемся реальном ряде даёт ложную/раннюю тревогу, и исправляет
   это подходящим для конкретной записи oracle-baseline — с итоговым
   сравнением эвристики, GNN и GAT по точности локализации;
10. `10_evaluation_orchestrator.ipynb` — `EvaluationCase`/`EvaluationOrchestrator`
    на одном случае с известной истиной (`has_truth=True`): hit/miss и ранг
    истинного источника.

Во всех ноутбуках используется фиксированный численный seed. Каждый маршрут
работает только со своим набором данных; граф зависимостей, локализация
источника и обучение GNN/GAT доступны исключительно для многоканального
случая, так как для одного канала эти этапы закономерно пропускаются
библиотекой. Ноутбуки 3–10 маршрута `n-d` используют oracle-assisted baseline
(известный `event_onset`) по той же причине, что и `1-d`: этот конкретный
ряд синтетический и размечен, что неприменимо к неразмеченным реальным
данным.
Результаты анализа сохраняются в игнорируемый каталог `results/1-d/` или
`results/n-d/` соответственно. Численные таблицы, manifest и анализ
чувствительности сохраняются отдельно от интерпретационного текста, чтобы
выводы можно было проверить.

#### Как `source_channel` и `event_onset` связаны в `kuramoto_propagation`

Блок `kuramoto_propagation` в `synthetic_datasets_metadata.json` описывает
один впрыснутый импульс, а не независимые события на каждом канале.
Механизм, шаг за шагом (реализация — `generate_kuramoto_propagation_series`
в `evt_demo.data_generator`):

1. **`event_onset`** выбирается один раз — для `source_channel`. Это индекс
   отсчёта, с которого начинается импульс на исходном канале; он выбран
   случайно из допустимого диапазона (`[n_points/4, n_points - duration -
   max_delay]`) отдельным seeded RNG, независимым от симуляции осцилляторов.
   Значение не зафиксировано: при другом `--seed`, `--source-channel` или
   `--delay-per-hop` оно изменится.
2. **`source_channel`** — канал, на котором генерируется сама форма импульса:
   сглаженный (tapered) всплеск Hurst/DFA-окрашенного шума
   (`_colored_noise` + `sin²`-окно), масштабированный на
   `event_magnitude_in_sigma`.
3. **Каналы расположены на кольце** (индексы `0..n_channels-1` замкнуты), поэтому
   `channel_arrival_delay[i] = ring_distance(i, source_channel) × delay_per_hop`.
   Отсюда симметрия и пик в середине массива: `channel_00` → 0 хопов,
   `channel_01`/`channel_11` → по 1 хопу (ближайшие соседи по кольцу), …,
   `channel_06` → 6 хопов (противоположная сторона кольца, `n_channels / 2`).
4. **Каждый остальной канал получает ту же форму импульса**, сдвинутую на его
   `channel_arrival_delay` и уменьшенную в `decay_per_hop ** hops` раз
   (по умолчанию `0.65` за хоп) — так, `channel_06` получает импульс на
   `30` отсчётов позже `channel_00` и с амплитудой около `0.65⁶ ≈ 7.5%` от
   исходной.

Итог: `event_onset` отвечает "когда началось на источнике", а
`channel_arrival_delay` (индексируемый по кольцевому расстоянию до
`source_channel`) — "насколько позже это увидел каждый канал". Вместе они
восстанавливают точное окно `[event_onset + delay, event_onset + delay +
event_duration)` для любого канала — это и есть окно, которое размечает
колонка `is_extreme` и рисует нижняя панель ("Ground-truth propagation
front") в `kuramoto_propagation_series.png`.

## Исследовательская дисциплина

- POT-порог проверяется анализом чувствительности; зависимые превышения требуют
  declustering, а неопределённость — блочного bootstrap.
- Статистическая связь локальной волатильности и экстремумов не доказывает
  причинность.
- Отчёт сохраняет seed, параметры, версию библиотеки и hash входных данных.
- Любое утверждение должно ссылаться на сохранённую таблицу или явно называться
  гипотезой.

## Как читать итоговую визуализацию

Верхняя панель показывает индикатор Graph-EVT, затенённый baseline, POT/GPD
alarm-порог и найденный момент устойчивого превышения. Средняя панель показывает
абсолютные робастные z-score каналов вокруг тревоги. Нижняя панель показывает
все вероятности локализации, а красным отмечает оценённый начальный источник.
Так различие между «EVT обнаружил событие» и «графовый этап предположил
источник» остаётся явным; ranking не доказывает физическую причинность.
